## Summary

The x-tail Karatsuba square reduces `hi·2^256` modulo p by doubling and
halving the 256-bit register `hi` 64 times in all. Each modular doubling adds
the constant `c = 2^256 − p = 2^32 + 977` under a control bit. In the base that
add ran a carry chain across all 255 positions. This commit sets one knob,
`KARA_SOL_DBL_FAST=1`, which routes those calls to `mod_double_inplace_fast`
and `mod_halve_inplace_fast`. On this route those use the carry-truncated
constant add with a 20-bit window, which stops the chain 20 bits above bit 32.
That cuts each call from 267 to 65 Toffoli: 202 × 64 = 12,928 Toffoli saved.
Qubits are unchanged.

The commit's comment calls the switch "value-exact". It is not: the truncated
add is wrong whenever a carry would run more than 20 bits past bit 32, about
2^-21 per call. The reroll pair was re-searched to (40, 13) for a clean test
set.

## What changed and why it saves Toffoli

1. **`KARA_SOL_DBL_FAST=1`**, new `set_default_env` line in
   `configure_ecdsafail_submission_route()`, `src/point_add/mod.rs`.
   - In `squaring_sub_from_acc_karatsuba()`, the closures `mod_dbl` and
     `mod_hlv` pick `mod_double_inplace_fast` / `mod_halve_inplace_fast` when
     `KARA_SOL_DBL_FAST=1`, and `mod_double_inplace_direct_const_fast` /
     `mod_halve_inplace_direct_const_fast` otherwise.
   - They are called 64 times in the Solinas reduction: 4 + 2 + 4 doublings
     for the `977` term, then 22 doublings and 22 halvings for the `2^32` term
     (the `ROUND84_XTAIL_BORROW_CARRIES` branch from [`287595e`](287595e.md)),
     then 10 halvings that restore `hi`. See
     [squaring-and-karatsuba](../concepts/squaring-and-karatsuba.md) and
     [modular-fold](../concepts/modular-fold.md).
   - A doubling rotates `hi` left (free), puts the old top bit in a fresh
     `ovf`, adds `c` controlled on `ovf`, and clears `ovf` with
     `cx(v[0], ovf)`. The halving is the mirror image with a controlled
     subtract. The only Toffoli are in the controlled constant add or subtract.
   - **Old path:** `cadd_nbit_const_direct_fast(v, c, ovf)`. It computes all
     255 carries. `c` has 7 set bits (0, 4, 6, 7, 8, 9, 32). A carry position
     costs 1 CCX, or 3 where `c` has a set bit, and position 0 costs 1. Its
     carries are cleared by measurement (`hmr` + `cz_if`), so the total is
     1 + 6 × 3 + 248 = 267 Toffoli per call.
   - **New path:** `mod_double_inplace_fast_with_dirty` checks
     `double_carry_trunc_window()` first. The route already sets
     `KAL_DOUBLE_CARRY_TRUNC_W=20`, so it calls
     `cadd_nbit_const_direct_trunc_fast(v, c, ovf, 20)` (and the halving calls
     `csub_nbit_const_direct_trunc_fast`). That adder stops the carry chain at
     `last = hi_bit(c) + 20 = 52`, so it computes 53 carries:
     1 + 18 + 46 = 65 Toffoli.
   - 267 − 65 = 202 per call, × 64 calls = 12,928, exactly the measured change.
   - The truncated add also holds 53 carry wires instead of 255, so the
     doubling lanes get narrower, not wider. The comment's "carry-ancilla"
     description does not match the code that runs. The square is not the
     binder, and the peak stays 1543.
2. **Reroll pair: `DIALOG_REROLL` 28 → 40, `DIALOG_POST_SUB_REROLL` 5 → 13.**
   Identity `X;X` counts that re-draw the 9,024 test inputs without changing
   the circuit (see [`ecbf87b`](ecbf87b.md)). The comment says a randomized 2-D
   search found it.

## Why it is still correct, and what it risks

The truncated add is approximate. It assumes no carry out of position 52.
That carry is nonzero only when a carry generated at or below bit 32 runs
through all of bits 33 to 52 of `hi`, which are then all 1. For a random `hi`
that is about 2^-21 per call. When it happens, the doubled value is wrong in
its top bits. The subtraction from `acc` then uses the wrong value (a classical
failure), and the halvings no longer undo the doublings, so `tmp_ext` is not
cleared (ancilla garbage). The carry wires themselves are always cleared,
because the truncated chain follows the same recurrence as the full one.

There are 64 such calls per shot, so the added λ is roughly
64 × 9,024 × 2^-21 ≈ 0.3 expected failing shots per draw. The reroll pair
(40, 13) draws a test set where every add is right: 9,024 of 9,024 shots pass,
0 classical, 0 phase and 0 ancilla failures. See
[nonce-island-and-lambda](../concepts/nonce-island-and-lambda.md) and
[comparator-and-width-truncation](../concepts/comparator-and-width-truncation.md).

## Classification rationale

The published label is Strength Reduction → fast-adder reroute: the knob
reroutes calls to the functions named `_fast`. But those already were "fast"
(measured-uncompute) adders. The saving comes entirely from the carry chain
being cut 20 bits above the constant's top bit, which is a probabilistic carry
truncation. Dead-Code and Redundancy Elimination → fold/carry truncation fits
the diff better. The published label is kept in the header.

## Reproduce

1. **Start from the base.** Clone https://github.com/ecdsafail/ecdsafail-challenge
   and run `git checkout 287595e -- src/point_add`.
   - The git parent is `7021abe` (anupsv). Diffing against it (50 lines) would
     revert that commit's `KARA_FREE_Z1_TOPBIT` lever and its schedule margin
     7 back to 5. This commit was built on `287595e`.
   - `git diff --ignore-cr-at-eol 287595e df83d16 -- src/point_add` is 12 lines
     in 1 file.
2. **Apply the patch below** from the repo root with `git apply --ignore-whitespace`.
   The flag lets the patch apply whether the files use LF or CRLF line endings.
   It is the complete diff against the base.
3. **Check the tree.** `git diff --ignore-cr-at-eol df83d16 -- src/point_add`
   should print nothing.
4. **Run the benchmark.** Run `./setup.sh && ./benchmark.sh` with no `DIALOG_*`,
   `KAL_*`, `KARA_*` or `ROUND84_*` environment variables set, because
   `set_default_env` keeps any value already in the environment. Expect:
   - 1543 qubits
   - 1,682,159 average Toffoli (rounded)
   - score 2,595,571,337
   - 0 classical, 0 phase and 0 ancilla failures

The score only reproduces with the reroll pair `DIALOG_REROLL=40`,
`DIALOG_POST_SUB_REROLL=13` and an identical op stream. Any other change needs
a new reroll search.
