## Summary

Each step of the dialog-GCD walk does a controlled subtract (forward) or add
(reverse) of `u` into `v` over the low `active_width` bits (background in
[8316db1](8316db1.md)). The body carry-band trim lets that subtract/add run a
few bits short on late steps, where `u` and `v` have already shrunk.
[004ffc0](004ffc0.md) set the trim list to `0,1`: no trim on the first half of
the walk, 1 bit on the second half. This commit sets it to `0,1,2`: three
bands, with trims of 0, 1 and 2 bits.

Each trimmed bit drops one gated-load Toffoli and one carry Toffoli. Over the
259 steps the trimmed total goes from 129 bits to 257 bits per walk. That is
128 more bits × 2 Toffoli × 4 walks = 1,024 Toffoli, exactly the measured drop.
Qubits are unchanged, and the tail nonce was re-hunted.

## What changed and why it saves Toffoli

All changes are in `src/point_add/mod.rs`, `configure_ecdsafail_submission_route()`.

1. **`DIALOG_GCD_BODY_CARRY_BAND_TRIMS`: `"0,1"` → `"0,1,2"`.**
   - `dialog_gcd_body_carry_band_trim(step)` (`rounds/dialog/mod.rs`) cuts the
     `dialog_gcd_active_iterations()` = 259 steps into bands of
     `ceil(259 / len)` steps.
   - Old, two bands of 130: steps 130–258 get trim 1. That is 129 trimmed bits
     per walk.
   - New, three bands of 87: steps 0–86 get trim 0, steps 87–173 get trim 1,
     and steps 174–258 get trim 2. That is 87 + 2 × 85 = 257 trimmed bits per
     walk.
   - `dialog_gcd_body_carry_trunc_width(active_width, step)` returns
     `body_w = max(active_width − trim, 2)`. In
     `dialog_gcd_controlled_sub_selected` / `..._add_selected`
     (no-carry-in body, `body_start = 1`), `body_len = body_w − 1` bounds:
     - the gated load `ccx(ctrl, u[1 + j], gated[j])`, 1 Toffoli per bit;
     - `cuccaro_{sub,add}_fast_borrowed_carries_no_cin`, 1 Toffoli per bit with
       carries erased by measurement;
     - the gated clear (`hmr` + `cz_if`), with no Toffoli.
   - So each trimmed bit is 2 Toffoli. Counting step by step, with the
     `active_width` schedule `ceil((256 − 1.014·step + 10) / 2)·2` (6 bits at the
     last step, so the floor of 2 never applies), gives 1,024 over the forward
     subtract and reverse add of both divisions.
   - The cswap and the branch comparator keep the full `active_width`.
2. **`DIALOG_TAIL_NONCE`: 201664 → 13362**, the fixed 48-pair `X;X` identity
   tail that reseeds the 9,024 test inputs.
3. The base's stale comment, which still said the trim was disabled, is
   replaced by a short one.

## Why it is still correct, and what it risks

The trimmed body leaves the top `trim` bits of the `active_width` window out of
the subtract or add. That is exact only if `u` and `v` are 0 in those bits and
no carry or borrow reaches them. The width envelope has a 10-bit margin over
the expected bit length, and the trim spends 1 or 2 of those bits, but only in
the body. An input whose operands still reach into the trimmed bits gets a
wrong `v`. Its GCD then does not reach the terminal state, which gives a
classical mismatch and usually ancilla garbage after the reverse walk.

Steps 87–129 are newly trimmed. These are earlier, wider steps than any trimmed
before, so the hazard grows. The commit comment calls it "value-clean on nonce
13362", which is the right way to put it. The classical pre-filter from
[88079e6](88079e6.md) does model the band trim, and the author used it to find
`13362`. That nonce draws a test set with 0 classical, 0 phase and 0 ancilla
failures over all 9,024 shots. See
[nonce-island-and-lambda](../concepts/nonce-island-and-lambda.md).

## Classification rationale

The census files this as comparator/width truncation. The same lever in
[004ffc0](004ffc0.md) and [cc5584e](cc5584e.md) is filed as fold/carry
truncation, because it drops the top bits of an adder's load and carry chain.
Either label fits: the trim acts like a body-only width margin. The two notes
are labelled differently only because the census labelled them differently.

## Reproduce

1. **Start from the base.** Clone https://github.com/ecdsafail/ecdsafail-challenge
   and run `git checkout 89abe1b -- src/point_add`.
   - Do not start from the git parent `e0767c7`. That is jackylee0424's
     apply-clean 19 commit, and this commit was not built on it.
   - Against the parent, the diff is 25 lines. It also reverts
     `DIALOG_GCD_APPLY_CLEAN_COMPARE_BITS` from 19 to 20 and the parent's nonce
     `60306`.
   - Against `89abe1b`, `git diff --ignore-cr-at-eol 89abe1b ace6347 -- src/point_add`
     is 19 lines in 1 file.
2. **Apply the patch below** from the repo root with `git apply --ignore-whitespace`.
   The flag lets the patch apply whether the files use LF or CRLF line
   endings. It is the complete diff against the base.
3. **Check the tree.** `git diff --ignore-cr-at-eol ace6347 -- src/point_add`
   should print nothing.
4. **Run the benchmark.** Run `./setup.sh && ./benchmark.sh` with no
   `DIALOG_*` or `R84_*` environment variables set, because `set_default_env`
   only fills in unset variables. Expect:
   - 1307 qubits
   - 1,488,188 average Toffoli (rounded)
   - score 1,945,061,716
   - 0 classical, 0 phase and 0 ancilla failures

The score only reproduces with `DIALOG_TAIL_NONCE=13362` and an identical op
stream. Any other change needs a new nonce hunt.
