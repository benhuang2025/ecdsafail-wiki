## Summary

Each step of the GCD apply adds `x` into `y` mod p (forward) or subtracts it
(reverse). After the raw 257-bit add or subtract, a Solinas fold adds or
subtracts `c = 2^32 + 977` in the low bits when the add overflowed. That fold's
carry ripple is truncated a window of `W` bits above bit 32. This commit makes
`W` 21 instead of 22, so each of the 518 folds per shot stops one carry
earlier. The saving is exactly 518 average Toffoli at the same 1313 qubits.
newjordan's sibling tree [`196d830`](196d830.md) had made the same cut before
the fold fusion. The tail nonce was re-hunted.

## What changed and why it saves Toffoli

All changes are default pins in `configure_ecdsafail_submission_route()`,
`src/point_add/mod.rs`.

1. **`KAL_FOLD_CARRY_TRUNC_W`: 22 → 21.**
   - Read by `fold_carry_trunc_window()`. When it is set, the
     `..._overflow_fold` and `..._underflow_fold` phases of the apply's
     controlled modular add and subtract
     (`dialog_gcd_cmod_add_materialized_pseudomersenne_chunked`,
     `dialog_gcd_cmod_sub_materialized_pseudomersenne_chunked`) call
     `cadd_nbit_const_direct_trunc_fast` or `csub_nbit_const_direct_trunc_fast`
     on `acc[..DIALOG_GCD_SPECIAL_ADD_LSBS]`, controlled by the overflow wire
     `acc_ovf`.
   - The truncated adder makes carry wires only for positions
     `0..=hi+W`, with `hi = 32`, the top set bit of `c`. Its carries are
     erased by `hmr` and `cz_if`, which costs no Toffoli. `c` has no set bits
     above 32, so the carry position that is removed costs exactly one CCX.
     See [modular-fold](../concepts/modular-fold.md) and
     [adders-and-carries](../concepts/adders-and-carries.md).
   - 259 steps × 2 apply passes = 518 folds per shot, which is the measured −518.
   - This window is separate from `KAL_DOUBLE_CARRY_TRUNC_W`, which controls
     the fused apply doubles and halves of [`8a47cf5`](8a47cf5.md).
2. **`DIALOG_TAIL_NONCE`: 44250004920 → 44575002764.**

## Why it is still correct, and what it risks

The truncated fold is wrong only when its carry runs through about 21
consecutive ones in `y` above bit 32 and leaves the window. That is about
2^−22 per call. The high bits of `y` then keep a stale value, which shows up
as a classical mismatch. The forward add and the reverse subtract use the
same window, so they stay exact inverses whenever no truncation fires. One
bit less doubles the per-call rate. The new nonce `44575002764` was found with
a CPU prefilter, and the trusted evaluation confirmed it clean: 9,024 of
9,024 shots, with 0 classical, 0 phase and 0 ancilla failures. See
[nonce-island-and-lambda](../concepts/nonce-island-and-lambda.md).

## Classification rationale

A carry window is narrowed by one bit. That is comparator/width truncation
(the census files fold-carry windows under it here), and the commit has no
other change.

## Reproduce

1. **Start from the base.** Clone https://github.com/ecdsafail/ecdsafail-challenge
   and run `git checkout 373fb4d -- src/point_add`. The base is the git
   parent. `git diff --ignore-cr-at-eol 373fb4d 974689f -- src/point_add` is
   4 lines in 1 file.
2. **Apply the patch below** from the repo root with `git apply --ignore-whitespace`.
   The flag lets the patch apply whether the files use LF or CRLF line endings.
   It is the complete diff against the base.
3. **Check the tree.** `git diff --ignore-cr-at-eol 974689f -- src/point_add`
   should print nothing.
4. **Run the benchmark.** Run `./setup.sh && ./benchmark.sh` with no
   `KAL_*` or `DIALOG_*` environment variables set. Expect:
   - 1313 qubits
   - 1,516,628 average Toffoli (rounded)
   - score 1,991,332,564
   - 0 classical, 0 phase and 0 ancilla failures

The score only reproduces with `DIALOG_TAIL_NONCE=44575002764` and an
identical op stream. Any other change needs a new nonce hunt.
