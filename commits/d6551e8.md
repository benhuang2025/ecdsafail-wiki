## Summary

Until now, carry-tail truncation (computing a constant adder's carry chain
only a few dozen bits past the constant's top set bit) was on only for the
controlled constant *subtractor*. Turning it on for the matching *adder*
`cadd_nbit_const_direct_fast` had always failed with phase garbage on all 141
batches. The comments blamed the adder's reverse sweep.

This commit finds the real cause. Some callers pass a dense constant, `p + 1`,
whose set bits reach bit 255. A window counted from bit 33 cuts that adder's
carry chain in the middle of the constant and drops real carries. The new
`kal_carrytail_count_c` starts the window above the top set bit of whatever
constant is passed. Dense constants then keep the full chain, and the sparse
Solinas constant `2^32 + 977` gets the cut. With that, carry-tail mode
defaults to `"both"`.

The shared window had to be re-tuned to 44 bits for the island, which widens
the subtractor's window from 26. Net: −22,925 average Toffoli at the same
2309 qubits.

## What changed and why it saves Toffoli

1. **New `kal_carrytail_count_c(n, c, enabled)`** in
   `src/point_add/kaliski_state.rs`.
   - The old `kal_carrytail_count` returns `cut = min(n − 1, K0 + W)` with
     `K0 = 33`.
   - The new one uses `k0 = max(K0, c.bit_len())`, so the window starts
     above `c`'s top set bit.
   - For `c = 2^32 + 977`, `bit_len = 33` and the cut is unchanged. For
     `c = p + 1`, `bit_len = 256` and the chain is full.
2. **`src/point_add/cuccaro.rs`, `cadd_nbit_const_direct_fast`**: the cut is
   now `kal_carrytail_count_c(n, c, kal_carrytail_add_enabled())`. The forward
   carry sweep, the sum XOR and the measured reverse sweep all use this one
   `cut`. The subtractor `csub_nbit_const_direct_fast` still uses
   `kal_carrytail_count`.
3. **`kal_carrytail_mode()`**: the default goes from `"sub"` to `"both"`, so
   `kal_carrytail_add_enabled()` is now true.
4. **`kal_carrytail_w()`**: a new first branch returns 44 when the add path is
   enabled, which is now the default. Before, the default was 26 on the
   swap-truncation tree. `W` is shared, so this sets both paths:
   - **ADD path, sparse `c`:** at `n = 256` the chain goes from 255 carry
     positions to `33 + 44 = 77`. That removes 178 positions per call. Above
     bit 32, each carry is `acc_i AND carry_i`, one CCX.
   - **SUB path:** the borrow chain grows from bit 59 to bit 77. That is 18
     more Toffoli per call, over about 611 calls, roughly +11,000.

   The sparse-constant adds are mainly the `+c` corrections of
   `mod_double_inplace_direct`, the Kaliski `r` doublings past
   `R_SMALL_THRESHOLD`, and of the low-scratch modular adders and Solinas
   folds in `modular.rs`.

## Why it is still correct, and what it risks

**Why the old ADD truncation failed.** In this adder, a carry above the
constant's top set bit can only propagate through a run of 1-bits of `acc`.
Bits where `c` has a 1 can generate a new carry. With `c = p + 1`, the set
bits run up to bit 255, so a window that ends at bit `33 + W` drops carries
that occur all the time. The high sum bits come out wrong. The note traces
the failure from there: a wrong sign bit feeds a later comparison, which
leaves a flag dirty, and resetting that flag with `free()` injects a random
phase. That gave the 141-of-141 phase failures. Starting the window above
`c.bit_len()` makes the truncation sound for any constant.

**Remaining risk.** For the sparse constant this is the same bet as on the
SUB path. A carry above bit 32 survives only through a run of 1s in `acc`.
The comments put the longest run seen in a 3M-trial Monte Carlo at 28 bits
for adds, which reaches bit 60. A 44-bit window reaches bit 76, so there are
about 16 bits of slack. A dropped carry would give a classical mismatch.

**Island.** There is no nonce in this era. The comment records a full
9,024-shot sweep of `W` with both paths on: 44 is clean, while 32, 36, 40,
49, 60, 90 and 140 fail. The failures come from the other approximate knobs
(W-TRUNC at margin 0, swap truncation) meeting a hard input in the new draw.
This draw is clean: 0 classical, 0 phase and 0 ancilla failures. See
[nonce-island-and-lambda](../concepts/nonce-island-and-lambda.md).

## Classification rationale

The saving comes from cutting carry chains in a constant adder, so
fold/carry truncation fits. The constant-aware window is the enabling fix.
It is what makes the cut sound for both constants.

+/// Constant-aware carry-tail count for the direct const ±c adders. Truncating
+/// at `cut` is exact only if no carry can reach bit `cut`; every set bit of `c`
+/// (with a |1> control) is a carry generator/propagator, so the window must
+/// start ABOVE c's top set bit. Anchor `k0 = max(env_k0, c.bit_len())`:
+///   * SPARSE Solinas c = 2^256 - p (top bit 32) keeps the tight truncation, but
+///   * DENSE c = p+1 (mod_neg/mod_double, top bit 255) gets the full chain
+///     (cut = n-1), the only sound choice — otherwise a dropped carry corrupts
+///     the high sum bits, poisons a sign-bit comparison, and the dirty flag's
+///     free()/R injects random global phase (the ADD-path 141 phase-garbage).
+/// Single-use, so forward sweep, sum XOR and reverse uncompute agree.
+#[inline]
+pub(crate) fn kal_carrytail_count_c(n: usize, c: U256, enabled: bool) -> usize {
+    if n <= 1 {
+        return n.saturating_sub(1);
